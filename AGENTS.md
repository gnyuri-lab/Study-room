## Решения, которые нельзя угадать

- Статусов пять: `not_submitted`, `submitted`, `revision`, `accepted`, `accepted_late`. Куратор выставляет только «сдано» и «на доработку»; **`accepted_late` система вычисляет сама** по времени сдачи против дедлайна. Отдельной кнопки у куратора нет (FR-47, BR-17…BR-19) — добавление кнопки ломает модель.
- Лимит попыток — **3**. Пересдача только из `not_submitted` и `revision`; из `submitted` запрещена до обратной связи куратора (FR-41, BR-14).
- Терминальные статусы меняет **только администратор** — возврат в `revision`; куратор не может (FR-48, BR-21).
- Пароль должен быть **обратно читаем администратором** (FR-09) — поэтому Fernet **плюс** pbkdf2-хеш. Не «улучшайте» это до одного лишь хеша: админ перестанет видеть пароль. Это принятый риск Р-01.
- Учётка админа по умолчанию `admin@admin.com` / `1234` с `must_change_password = 1`: до смены логина и пароля рабочие экраны недоступны (FR-02).
- Уникальность e-mail — **в пределах курса**, регистронезависимо (BR-06); один e-mail на двух курсах → выбор курса при входе (FR-05).
- Длина пароля: администратор ≥ 8 символов, студент и куратор ≥ 5.
- Удаление: курс — физический каскад с перечнем последствий и вводом названия, записи журнала сохраняются с обезличиванием автора; задание или группа **со сдачами** — только архив; непустую группу удалить нельзя; IP-адреса в журнал не пишем (FR-64).
- Файлы: 10 МБ (`10 485 760` байт), до 5 на задание и 5 на сдачу, типы `xlsx, xls, docx, pdf, csv, txt, md, png, jpg, zip`, проверка по расширению **и** по содержимому, хранение под сгенерированным именем (FR-51…FR-54, NFR-06).

## Схема SQLite 3

Полные поля и валидации — `ТЗ_MVP.md` §7.1–§7.14. Ниже то, что не видно из имён таблиц.

| Таблица | Назначение | Неочевидное |
|---|---|---|
| `users` | учётные записи всех ролей | `course_id` NULL только у `admin`; e-mail уникален **в пределах курса** и регистронезависимо; хранятся **оба** поля — `password_enc` (Fernet) и `password_hash` (pbkdf2). Без `password_enc` админ не увидит пароль (FR-09), не «приводите» схему к одному хешу |
| `courses` | курсы | архива нет: у курса только каскадное удаление; статус «черновик» не вводим (В-05) |
| `groups` | группы курса | `name` уникален в пределах курса; `archived_at` — мягкое удаление |
| `group_members`, `curator_groups` | членство | в `group_members` только роль `student`, в `curator_groups` только `curator`; уникальна пара `(group_id, user_id)`; один куратор может быть в нескольких группах |
| `assignments` | задания | `due_at` допускает NULL — дедлайн необязателен; `order_index` задаёт порядок вывода; `archived_at` — мягкое удаление при наличии сдач |
| `assignment_files`, `submission_files` | вложения | путь хранения в БД не хранится: `stored_name` — сгенерированное имя, `original_name` — только для показа; `size_bytes` ≤ 10 485 760 |
| `submissions` | попытки сдачи | одна строка = одна попытка; `attempt_no` уникален в паре `(assignment_id, student_id)`; статус «не сдано» не хранится — это отсутствие строки (Д-10) |
| `submission_comments`, `submission_comment_files` | переписка и файлы к комментариям | вложение привязано к комментарию (`comment_id`), а не к сдаче (FR-46), до пяти файлов на комментарий; отдельной таблицы файлов в записке нет, она выведена из брифа |
| `action_log` | журнал действий | `actor_id` становится NULL при обезличивании после удаления курса, запись сохраняется; `details_json` без паролей; колонки IP нет (FR-64) |
| `import_batches`, `import_errors` | отчёты импорта | `row_number` считается с 2 — строка 1 это заголовок; на одну строку может быть несколько ошибок |

Что легко нарушить при реализации:

- Регистронезависимая уникальность e-mail: обычный `UNIQUE` в SQLite регистр учитывает, нужен `COLLATE NOCASE` либо отдельная нормализованная колонка в составном `UNIQUE(course_id, …)`.
- Один e-mail на двух курсах допустим (две строки `users`), поэтому уникальность составная, а не глобальная; вход при этом требует выбора курса (FR-05).
- Статусы (`not_submitted`, `submitted`, `revision`, `accepted`, `accepted_late`) и роли (`admin`, `curator`, `student`) хранить кодами из §7.1–§7.2, подписи — только в интерфейсе.
- `action` и `entity_type` в журнале берутся из справочника §7.12; новые значения не добавлять молча.
- Схема применяется скриптами `migrations/001_schema.sql`, `002_indexes.sql` (индексы на `email`, `course_id`, `status`, `created_at`), `003_comment_files.sql` (файлы переписки на `comment_id`, до пяти файлов на комментарий — §7.10, FR-46) и `004_action_log_codes.sql` (коды `backup.exported`/`backup.restored`, сущность `backup` — §7.12, FR-69; пересборка `action_log`, потому что SQLite не меняет CHECK); ORM не используется. Недостающие миграции к существующей базе применяет `create_app` при старте (§12.1, фикс Э-10: база версии 3 роняла экспорт 500 на CHECK журнала) — базу без файлов по-прежнему готовит только `init-db`.
