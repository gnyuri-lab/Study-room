## 2. Продуктовые выводы

**Суть продукта.** Перенести уроки, домашние задания и сдачу работ из почты и чатов в единый учебный кабинет. Три роли: администратор, куратор, студент. Ключевая ценность — автоматический прогресс по статусам вместо ручных xlsx-отчётов и конфликтов из-за них.

**Пять статусов работы:** не сдано · на проверке · на доработку · сдано · сдано после дедлайна.

**Матрица прав (из брифа):**

| Возможность | админ | куратор | студент |
|---|---|---|---|
| CRUD курсов, групп, заданий, файлов | ✓ | — | — |
| Импорт списка группы с валидацией | ✓ | — | — |
| Удаление курса с каскадом | ✓ | — | — |
| Дашборд с диаграммами прогресса | все курсы | только свои группы | — |
| Список студентов группы с e-mail и паролем | ✓ | **не видит** | только себя |
| Просмотр и повторная выдача паролей | ✓ | — | — |
| Скачивание материалов задания | ✓ | ✓ | ✓ |
| Сдача работы, комментарий, вложение | — | — | ✓ |
| Постановка статуса, комментарий, вложение к работе | — | ✓ | — |
| Пересдача работы | — | — | ✓ |
| Отзыв уже выставленного статуса | ✓ | — | — |
| Журнал действий | ✓ | — | — |

**Обязательные механики из брифа:**
- Первый вход `admin@admin.com` / `1234` с обязательной сменой логина и пароля с подтверждением.
- Создание курса: название → задания (название, описание вручную или импортом из файла, вложения) → предпросмотр по кнопке «Сохранить» → подтверждение.
- Редактирование курса: «Изменить курс» / «Удалить курс» (с подтверждением) / «Добавить группу» / «Изменить группу».
- Импорт группы: сохраняются **только корректные строки**; показывается число корректных строк, номера строк с ошибками и суть ошибок.
- Правила импорта: все поля заполнены; e-mail содержит `@` и домен; e-mail уникален; дублей нет.

**Учебный контент (3 ДЗ).** Все три задания устроены одинаково: лист «Исходные данные и модель» (студент вводит жёлтые ячейки, формулы зелёные) + лист «Расчёт (проверка)» (пошаговый пересчёт для куратора). Сдача — заполненный файл `ФИО_ДЗN.xlsx` плюс ответы на три контрольных вопроса в комментарии. **Контрольное отклонение между листами должно быть 0 %.**

| № | Тема | Что внутри | Срок |
|---|---|---|---|
| 1 | DCF | WACC через CAPM, FCF, TV по Гордону, EV, Equity | 26.09.2026 (уже истёк) |
| 2 | Мультипликаторы | 5 аналогов, EV/EBITDA, P/E, EV/Sales, P/BV, медианы, приведение к Equity | 10.10.2026 |
| 3 | Капитализация | Нормирование дохода, кумулятивная ставка R, связь `R = WACC − g`, сравнение с результатом ДЗ №1 | 01.11.2026 |

Легенда цветов: жёлтый — ввод, зелёный — формула, серый — задано, оранжевый — итог.

**Связь между ДЗ №3 и ДЗ №1.** В ДЗ №3 ученик вручную вносит результат DCF из ДЗ №1; лист автоматически считает отклонение капитализации от DCF в процентах. Значит, модель не изолирована — это живой учебный сценарий.

**Проверено расчётом:** все три листа «Расчёт (проверка)» математически согласованы с листом 1, то есть контрольное отклонение 0 % достижимо без дополнительных правок формул. Вычислять формулы в приложении **не требуется** — файлы хранятся и скачиваются как есть.

## 3. Технические выводы

**Ограничения MVP (жёсткие).** Без платного хостинга, без реальной отправки писем и сообщений, без интеграции с CRM, без генерации PDF, без внешних AI и API. Стек — HTML + CSS + JS + БД либо аналогично простой с обоснованием. Демо — локально в браузере. Адаптив от 360 px, браузеры Chrome / Edge / Safari / Yandex. Только вымышленные данные, никаких секретов в репозитории, никаких паспортных и платёжных данных. **Публичный запуск вне MVP** — юридические тексты и политика обработки персональных данных не согласованы.

**Находка по реестрам: пароли записаны формулами.** В столбце «пароль» лежит не текст, а формула вида `=LEFT(D2,4)&F2`, где `F` — служебный символ в соседнем столбце. Проверено чтением файла: Excel сохранил кэшированные значения, поэтому библиотека чтения xlsx в режиме «значения» отдаёт готовые пароли (`maka!`, `lari@`, `krut&`, `trus\`, `sher*`, `medv%`, `rubl?`, `nest@`, `gnyu@`). Это нужно учесть в импорте — читать значения, а если кэша нет, уметь посчитать этот узкий шаблон самому, иначе файл, созданный программно, не прочитается.

**Заложенные дефекты реестров как тест-кейсы.** В файле `Список студентов-ФК_21.xlsx` намеренно оставлены две дефектные строки, совпадающие с правилами импорта из брифа:

| Файл | Строка | Персона | Дефект |
|---|---|---|---|
| ФК_21 | 5 | Рублев Андрей | пароль не заполнен вовсе (ячейка пуста) |
| ФК_21 | 6 | Болт Алекс | не указана группа; e-mail `rubl@tn.sp` дублирует строку 5 |

**Актуальное состояние реестров зафиксировано 27.09.2026.** Файл `Список студентов-ФК_11.xlsx` принят без замечаний: куратору `Nest Yuri` проставлена группа `ФК11`. В `Список студентов-ФК_21.xlsx` куратор переименован из `Nest Yuri` в `Нест Борис`, поэтому прежнее расхождение «один человек с двумя e-mail в разных файлах» больше не возникает. Оба файла пригодны как эталонные тест-фикстуры: первый — для проверки чистого импорта, второй — для проверки отбраковки строк.

**Следствие для правила длины пароля.** Порог «минимум 5 символов» согласуется с данными: все заполненные пароли в реестрах ровно 5 символов, а пустой пароль у «Рублева» отсеивается сразу по двум правилам — «все поля заполнены» и «минимум 5 символов». Совпадение подтверждает, что порог выбран верно.

## 4. Принятые решения

### 4.1 Стек

**Python 3.12 + Flask 3 + SQLite + Jinja2 + ванильный JavaScript, без внешних CDN и сетевых API.**

Обоснование, требуемое брифом: единый процесс, запуск одной командой локально в браузере; SQLite — файл рядом с приложением, бесплатна, не требует хостинга; Jinja2 даёт серверный рендер без SPA-сборщика; диаграммы рисуются собственным SVG-кодом, поэтому приложение полностью работает офлайн и не нарушает запрет на внешние API.

Зависимости: `flask`, `openpyxl` (только импорт реестров), `python-docx` (импорт описаний), `cryptography` (шифрование паролей — см. 4.4), `pytest` (тесты). Все бесплатны и ставятся через pip.

### 4.2 Схема данных

`users` (внутрикурсовые), `courses`, `groups`, `group_members`, `curator_groups`, `assignments`, `assignment_files`, `submissions`, `submission_files`, `submission_comments`, `action_log`, `import_batches`, `import_errors` + представление текущего статуса по паре «студент × задание».

### 4.3 Политика паролей

- Администратор задаёт себе пароль: **минимум 8 символов**.
- Администратор задаёт пароли студентам и кураторам: **минимум 5 символов**.
- **Пароль ученика и куратора виден администратору** и может быть выдан повторно.
- **Студент и куратор могут сменить свой пароль самостоятельно** (в брифе не описано, но без этого утерянный пароль не вернуть).
- Сценарий восстановления: ученик обращается к администратору → администратор открывает карточку, видит текущий пароль или назначает новый → ученик входит и при желании меняет его сам. Каждое такое действие попадает в журнал аудита.
- Куратор **не видит** паролей — только администратор.

### 4.4 Хранение паролей (компромисс, требующий внимания)

Требование «админ видит пароль» несовместимо с необратимым хешированием. Поэтому пароль хранится **обратимо** — зашифрованным симметричным шифром (Fernet, библиотека `cryptography`), ключ лежит в локальном файле конфигурации **вне репозитория**. Проверка при входе — расшифровка и сравнение в постоянном времени; рядом хранится и хеш для быстрой сверки.

Это осознанный компромисс под пилот с вымышленными данными. В записке о рисках он отмечен явно: при переходе к реальным пользователям видимость пароля нужно убрать, оставив только сброс администратором. Ключ и пароли в репозиторий не попадают — требование брифа соблюдено.

### 4.5 Уникальность e-mail

**В пределах курса, а не глобально.** Один и тот же человек может числиться на разных курсах под одним e-mail.

Следствия, заложенные в схему:
- Учётная запись `users` принадлежит курсу; у администратора курс пустой (системная учётная запись).
- При входе по e-mail, если найдено несколько курсов, пользователю предлагается выбрать курс.
- Первое вхождение e-mail в файле считается исходным, последующие — дублями.
- **Важное следствие:** правило «только e-mail» из брифа не запрещает расхождение ФИО. Если в одном курсе появятся две учётные записи с разными e-mail, но одинаковым ФИО, правилами они не отсеются — это формально разные люди. Администратор обязан обращать внимание на совпадение имён в отчёте импорта. Отдельного правила на совпадение ФИО бриф не задаёт, поэтому в MVP оно не проверяется.

### 4.6 Пересдача и лимит попыток

- Лимит — 3 попытки на задание, настраивается одной константой.
- Новая сдача разрешена только из статусов «не сдано» или «на доработку» и при неисчерпанном лимите.
- Из статуса «на проверке» пересдача запрещена: сначала куратор должен дать обратную связь.
- Статусы «сдано» и «сдано после дедлайна» — терминальные.
- Каждая попытка сохраняется отдельной записью, вся история версий видна в карточке задания.

### 4.7 Автостатус «сдано после дедлайна»

Кнопки у куратора нет: он нажимает «Сдано», сервер сравнивает время сдачи с дедлайном и, если сдача позже, сохраняет статус «сдано после дедлайна». Логика серверная, с записью в аудит.

### 4.8 Отзыв проверки

Терминальные статусы меняет **только администратор**: он может вернуть принятую работу в «на доработку». Куратор терминальные статусы не трогает.

### 4.9 Удаление

- **Курс** удаляется физически с каскадом (бриф: «удаляются все данные по курсу»), но с явным подтверждением и перечислением того, что будет удалено. Записи журнала аудита сохраняются с обезличенным автором.
- **Задание и группа** удаляются мягко (в архив), если по ним есть сдачи, — чтобы работа студентов не пропала безвозвратно. Полное удаление доступно только при отсутствии сдач.
- **Группу с непустым составом удалить нельзя** — операция блокируется с объяснением.
- Дедлайны задаются администратором вручную, с подсказкой из текста описания ДЗ.

### 4.10 Правила вложений

Хранятся в `instance/uploads/` под случайными именами, оригинальное имя только в базе; проверка прав при скачивании для каждой роли; ограниченные типы файлов, лимит 10 МБ на файл и не более 5 файлов на задание и на сдачу; имя файла никогда не участвует в построении пути.

### 4.11 Аудит

Пишутся вход и выход, смена учётных данных, **просмотр и повторная выдача пароля администратором**, создание, изменение и удаление курсов, групп и заданий, импорт с перечнем ошибок, сдача работы, смена статуса с указанием предыдущего и нового, скачивание и удаление файлов. IP-адреса **не пишутся** — для локального пилота они избыточны. Экран администратора: таблица с фильтрами и выгрузкой в CSV.

### 4.12 Демо-данные

Один курс, две группы по пять студентов, куратор на обе группы, предзаполненные сдачи всех состояний, чтобы дашборды были непустыми. Студенты демо-групп — **отдельные вымышленные персоны**, не совпадающие с реестрами: файлы реестров остаются нетронутыми и служат тест-фикстурами для проверки импорта.

**Состав четырёх заданий демо-курса:**

| № | Задание | Файл | Дедлайн | Зачем нужно |
|---|---|---|---|---|
| 1 | ДЗ №1 — оценка методом DCF | `ДЗ1_DCF.xlsx` | в прошлом | показать автостатус «сдано после дедлайна» |
| 2 | ДЗ №2 — оценка по мультипликаторам | `ДЗ2_Multiples.xlsx` | будущий | обычный сценарий сдачи |
| 3 | ДЗ №3 — капитализация дохода | `ДЗ3_Capitalization.xlsx` | будущий | кросс-зависимость с ДЗ №1 |
| 4 | Тестовое задание без файла | — | будущий | проверить сдачу без вложения |

Второй курс не создаётся — его заводит сам заказчик через импорт реестров, это и есть проверка.

## 6. Критерии приёмки

1. Первый вход `admin@admin.com` / `1234` требует смены логина и пароля с подтверждением.
2. Создание курса, заданий и файлов проходит через форму с предпросмотром и подтверждением.
3. Импорт списка сохраняет только корректные строки и показывает номера строк с ошибками и суть ошибок.
4. Студент видит только свои курсы, группы, задания и дедлайны.
5. Куратор видит только свои группы и не видит e-mail и пароли.
6. Администратор видит все курсы, группы, задания, списки, а также пароли и может выдать их повторно.
7. Студент и куратор могут сменить свой пароль самостоятельно.
8. Сдача после дедлайна автоматически получает статус «сдано после дедлайна».
9. Пересдача доступна после статуса «на доработку», не более трёх попыток и не из статуса «на проверке».
10. Терминальный статус меняет только администратор.
11. Сдатые работы не пропадают при удалении задания или группы: используется архив.
12. Группу с непустым составом удалить нельзя.
13. Один e-mail может быть на разных курсах; в пределах одного курса он уникален.
14. Все ключевые действия попадают в журнал аудита; IP-адреса не пишутся.
15. Файлы не скачиваются теми, у кого нет прав; лимиты и типы соблюдаются.
16. Пароль администратора короче 8 символов и пароль студента короче 5 символов отклоняются с понятным сообщением.
17. Интерфейс работает от ширины 360 px в Chrome, Edge, Safari и Яндекс.Браузере.
18. Автотесты проходят, в репозитории нет секретов, запуск локально без интернета.

## 7. Риски

| Риск | Влияние | Решение |
|---|---|---|
| Видимость паролей администратором снижает защиту | Высокое | Осознанно принято под пилот с вымышленными данными; ключ вне репозитория; при переходе к реальным пользователям видимость убирается |
| Удаление курса каскадно уничтожит сданные работы | Высокое | Подтверждение с перечислением и требованием ввода названия курса; аудит сохраняется |
| Правило уникальности по e-mail не ловит расхождение ФИО внутри курса | Среднее | Риск зафиксирован; администратор проверяет глазами отчёт импорта |
| Импорт формул в столбце «пароль» сломается на файлах без кэша | Среднее | Чтение значений с запасным вычислением шаблона и понятной ошибкой |
| Все три ДЗ содержат «дёшевые» формулы, реальная проверка знаний остаётся на кураторе | Среднее | Статусы и комментарии куратора обязательны; диаграммы показывают, где ручная проверка проседает |
| Список из 3 файлов не отражает реальный по величине курс | Среднее | Загрузка любых файлов; второй курс проверяется вручную |
| Диаграммы на ванильном JS займут больше времени, чем библиотека | Низкое | Три простых типа диаграмм, без сложных осей |
